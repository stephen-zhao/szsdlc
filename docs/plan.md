# Agentic SDLC Framework (`szsdlc`) — Implementation Plan

> **For agentic workers:** implement task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a **project-agnostic** agentic SDLC framework, distributed as a
Claude Code plugin plus a CLI, in which every fact about work is stated once in
a machine-readable record and every index, list, board, roadmap, back-link and
cross-reference is generated by script rather than by model reasoning.

**Non-goal:** anything specific to any one consuming project. No environments,
no dev/prod, no infrastructure vocabulary, no domain ledgers as built-in
concepts. Project-specific structure is expressed through configuration and
templates only. The framework's first consumer is the `s-s1-lab` homelab
infrastructure repo, but nothing about that repo may leak into the design.

**Architecture:** Everything trackable is an **entity** with an opaque
identifier — `<TYPE>-<NNNN>` (`WI-0042`, `REQ-0007`, `IDEA-0113`), one form
everywhere. Each entity type is declared in project config with its own prefix,
counter, schema, workflow, storage layout and directory. Ideas enter typeless
and cheap, and refinement **spawns** typed entities from them. Work is grouped
on two independent axes, both metadata rather than identifier: **tags**
(free-form, many per item — what this touches) and **epic** (a `parent`
relation — toward what outcome). Placement lives in **one roadmap record** of horizon
buckets, not as a field smeared across every entity. A `szsdlc` CLI performs
every deterministic operation; Claude Code hooks make those operations
automatic and the gates non-optional; skills carry only judgment.

**Tech stack:** Python 3.10+ (PyYAML, Jinja2, jsonschema), Claude Code plugin
(skills + hooks), JSON Schema.

**Research basis:** [`research.md`](research.md) (Plan C).

**Decisions taken:**

| Decision | Choice | Rationale |
|---|---|---|
| Name | `szsdlc` — repo, plugin, CLI | User choice |
| Location | `E:\Projects\Dev-kyle\szsdlc` | Standalone repo — **created, Task 1 complete** |
| Distribution | Claude Code plugin, listed in the existing `szccpmp` marketplace | A marketplace entry may reference a plugin in a *different* repo via a `github` source, pinned independently. **No submodule required** |

A type prefix plus a sequential number is the accepted exception and matches requirements-engineering convention |
| **Grouping similar work** | **Free-form `tags`**, multi-valued, no declaration required | Work routinely spans two concerns, and a single-valued taxonomy forces an arbitrary pick. Tags need no config, no display form, and no rename when something is refiled |
| Tag hygiene | Normalized on write; `validate` warns on near-duplicates and singletons | Free tags fail by silently splitting `dns` / `DNS` / `dsn`. Normalization plus a warning buys taxonomy hygiene without a declaration burden |

| Type in the ID | Accepted, with `convert` as the escape hatch | JIRA keeps type out of the key so reclassification is free. We take the opposite trade for legibility, since our types carry different schemas and workflows. Typeless intake (below) means normal work never needs `convert` |

| **Refinement** | Ideas **spawn** typed entities via a relation; the idea persists as provenance | One idea may yield several entities; nothing is lost or renamed, and no tombstone is needed |
| **Storage layout** | Per-type: `file` for low-fidelity types, `directory` for types with artifacts | A one-line thought should not cost a directory |
| **Roadmap** | One record with horizon buckets, written only by `schedule`/`unschedule`; **no `priority` field on entities** | Rescheduling edits one file instead of N. Placement is a single fact with a single home — the same rule as every other index |
| Entity types | Configurable; six shipped as replaceable defaults, each declaring capability flags rather than relying on its name | Idea, epic, requirement, spike, work item and decision are generic SDLC concepts |
| Requirements | Definitional, not work: no progress states, never in `next`, never a parent, never archived. Coverage and delivery are **derived from links**, never stored | Matches 29148-aligned tooling practice; storing them recreates the stale-state bug the framework exists to remove |
| Grouping axes | Two, independent, both metadata: **tags** (what this touches) and **epic** (toward what outcome, via `parent`) | Tags are many-per-item and cheap; an epic is a single deliberate bundle with its own lifecycle. Neither belongs in an identifier, and neither substitutes for the other |
| Relations | Stated on one side only; inverses generated | DRY — the back-link is rendered, never authored |
| Task tracking | Markdown checkboxes, parsed for progress | One format, readable by human and script |
| Git automation | Out of scope for v1 | Keeps the framework forge-agnostic |

## Core model (all generic)

| Concept | Storage | Notes |
|---|---|---|
| **Entity** | `file` layout: `<dir>/<ID>-<slug>.md`. `directory` layout: `<dir>/<ID>-<slug>/entity.md` | Frontmatter is the only hand-authored state |
| **Artifacts** | further files in a `directory`-layout entity | Optional; presence can gate transitions |
| **Relations** | `relations:` in frontmatter | Typed, cross-entity, validated globally, inverses generated |
| **Roadmap** | `<roadmaps>/<name>.yml` — horizon buckets of ids | The single home for priority *and* schedule placement |
| **Views** | generated markdown, written only by `sync` | inbox, board, roadmap, rollups, registers, traceability |
| **Records** | project-defined YAML dataset + template → generated markdown | Generic mechanism for any project-specific tracked table |
| **Standards** | `<standards>/*.md` with `applies_to` globs | Matched and injected on demand, never preloaded |

### Capability flags

Entity types are not all the same *kind* of thing, and the framework must not
hardcode which is which. Each type declares flags, and the flags — not the type
name — drive behaviour:

| Flag | Meaning |
|---|---|
| `layout` | `file` or `directory` |
| `intake` | accepts typeless capture; appears in the inbox view |
| `actionable` | appears in `szsdlc next` |
| `tracks_progress` | has a checkbox artifact parsed for progress |
| `can_parent` | is a legal `parent` target |
| `schedulable` | may be placed on a roadmap |
| `persistent` | never archived when work around it completes |

### Default entity types (replaceable wholesale via config)

| Prefix | Type | Default workflow | layout | intake | action­able | progress | can_parent | schedulable | persistent |
|---|---|---|---|---|---|---|---|---|---|
| `IDEA` | idea (typeless intake) | `inbox → refining → refined \| dropped` | **file** | **yes** | no | no | no | no | no |
| `EPIC` | epic (grouping of work) | `open → active → closed` | directory | no | no | derived | **yes** | yes | no |
| `REQ` | requirement (product definition) | `draft → reviewed → approved → superseded \| retired` | directory | no | no | **none** | no | no | **yes** |
| `SPK` | spike (investigation) | `open → researching → answered` | directory | no | yes | no | no | yes | no |
| `WI` | work item (unit of delivery) | `idea → groomed → ready → designing → planned → executing → review → done` (+ `dropped`) | directory | no | yes | yes | no | yes | no |
| `ADR` | decision | `proposed → accepted → superseded` | directory | no | no | none | no | no | **yes** |

`REQ` and `ADR` land on identical flags — both are long-lived definitions
rather than work — which is a good sign the flags carve at the joint rather
than encoding type names.

**REQ is a definition, not a unit of work.** Its lifecycle describes the
validity of the *statement* and never its delivery. `EPIC` is the grouping of
work; `REQ` is the specification of the product. A work item carries both a
`parent` (exactly one epic) and `implements` (zero or more requirements).

### Frontmatter

```yaml
---
id: WI-0042                  # opaque; never encodes classification
title: Short imperative title
tags: [dns, tls]             # free-form, many per item, retag freely
status: executing            # from this type's configured workflow
relations:
  parent: EPIC-0011          # exactly one epic; inverse `children` GENERATED
  implements: [REQ-0007]     # zero or more; inverse GENERATED
  depends_on: [WI-0038]
  refined_from: IDEA-0113    # provenance, written at spawn
opened: 2026-08-16
---
```

A requirement carries no work state at all — no progress, no schedule placement,
no ordering:

```yaml
---
id: REQ-0007
title: Every service is reachable over TLS trusted by managed clients
tags: [tls]
status: approved             # definition lifecycle only
---
```

Its `implemented_by`, `covered` and `delivered` are all generated. Nothing is
written to `REQ-0007` when work against it starts or finishes.

### Derived attributes (never stored)

Requirements-engineering tooling aligned to **ISO/IEC/IEEE 29148:2018**
(Edition 2 — the 2011 first edition is withdrawn) computes coverage and
verification from traceability links rather than storing them, and storing them
here would recreate exactly the stale-state problem this framework exists to
remove. The split those tools draw is the one adopted here: an entity *stores*
its own definition status and *derives* everything about delivery. Entity types
may therefore declare **derived** attributes, evaluated from the relation graph
at render time:

| Derived on | Attribute | Computed from |
|---|---|---|
| `REQ` | `covered` | at least one entity `implements` it |
| `REQ` | `delivered` | every implementing work item is terminal |
| `EPIC` | `progress` | aggregate over `children` |
| `IDEA` | `refined_into` | entities spawned from it |

`szsdlc list --type REQ --uncovered` is then a graph query, so an approved
requirement nobody has implemented is impossible to lose track of, and an epic
never stores a percentage that can go stale.

## Two kinds of validity

`sync` renders an invalid project happily; `validate` is what objects. That is
only coherent because *project* validity and *model* validity are different
things:

| Layer | May be invalid? | Detected by | Means |
|---|---|---|---|
| **Model invariants** | **Never** | assertions and structure; a violation is a `szsdlc` **bug** | program error, reported as an internal error — never a finding |
| **Project state** | Routinely, and legitimately mid-edit | `validate` | the user's work is inconsistent |
| **Unparseable input** | Yes | the load layer, represented explicitly | a file is broken |

The model stays valid **by representing invalidity explicitly**, which is the
mechanism rather than a contradiction:

- A relation is `(source, kind, target-string)`. The target is held **as
  written** and resolved lazily — you cannot report a dangling reference you
  refused to represent.
- A file whose frontmatter will not parse becomes an explicit *unparseable
  entity* node rather than an exception, so one corrupt file cannot block
  `sync` for every other entity.
- A status outside the configured workflow is held as-is. `set` refuses to
  *create* one, but a hand-edited file may contain one and must still load.

Two consequences the implementation must honour:

**Views degrade visibly, never silently.** A dangling reference renders as
`WI-0420 (missing)`; an unparseable entity appears in the view with its path.
Dropping broken edges would let `sync` conceal precisely what `validate` exists
to surface.

**`sync` requires only model validity.** "Can I load and render this?" — not
"is this project coherent?". That is why it can, and must, run against a
half-built graph.

## Standards

A **standard** is one convention this project follows, written as a short
markdown file with a glob saying where it applies:

```markdown
---
applies_to: ["<glob>/**"]
---
Templates live at <path>. Never hardcode a version; reference the pinned
digest instead.
```

Standards exist to solve a measured problem. The BMAD cost analysis attributes
**80%+ of token spend to re-injecting the same standards documents into every
agent invocation**, and Agent OS's answer — discover, index, inject only what
matches — reports 200–500 tokens per injection. The equivalent today is a
conventions section in `CLAUDE.md` that loads in full every session no matter
what is being touched, and grows monotonically because nothing ever justifies
deleting a line.

**Injection is by hook, not by hope.** A `PreToolUse` hook on `Edit|Write`
matches the target path against every standard's `applies_to` and returns the
matches as `additionalContext`. Editing a template pulls in the template
conventions, at the moment of editing, and nothing else. A convention that
depends on the agent remembering to look it up is not a convention.

This is the one part of the framework that replaces existing `CLAUDE.md`
content rather than adding something new, so it is also the part most likely
to be cut if it does not earn its keep.

## Intake and refinement

The inbox must accept anything from a single bullet to a page of related
thoughts, at a cost low enough that capturing is never a decision.

```bash
szsdlc capture "valkey needs a sentinel quorum story"     # one line
szsdlc capture < notes.md                                 # a page of thoughts
szsdlc capture                                            # opens $EDITOR
```

Each produces one file — `ideas/IDEA-0113-valkey-sentinel-quorum.md` —
with the minimum viable frontmatter. Title is derived from the first line when
not given; the body is free-form and never parsed.

```yaml
---
id: IDEA-0113
status: inbox
captured: 2026-08-16
---
```

**Refinement spawns typed entities rather than converting the idea.** The idea
is provenance and stays put:

```bash
szsdlc refine IDEA-0113 --into SPK --title "Sentinel quorum under partition"
szsdlc refine IDEA-0113 --into WI  --title "Add sentinel quorum config"
```

Each spawn writes `refined_from: IDEA-0113` on the **child** — the single
authored side — and the idea's `refined_into` list is generated. One idea
yielding three entities is the normal case, which is what "a set of related
thoughts" requires. When at least one child exists the idea advances to
`refined`; ideas that go nowhere are `dropped` with a reason, never deleted, so
the same thought arriving twice is recognisable.

This is also why typed intake would have been wrong: nothing is ever
misclassified at capture, so `convert` is reserved for genuine reclassification
of already-typed entities rather than being on the common path.

## Prioritization and roadmapping

Placement is a fact about a *set*, not about a member, so it does not live on
entities. There is no `priority` field. One record holds both ordering and
horizon:

```yaml
# roadmaps/roadmap.yml
now:
  - WI-0042
  - SPK-0003
next:
  - EPIC-0011
later:
  - WI-0051
```

Horizons are named and ordered in config (`now / next / later` by default, or
release names, or dated milestones — the framework does not care). More than
one roadmap is allowed, so a project can keep a global roadmap alongside a
per-epic one without either becoming the other's copy; the `--roadmap` flag
defaults when only one exists.

Scheduling is a single verb with a single ref, never a hand edit:

```bash
szsdlc schedule WI-0042 --horizon now --after SPK-0003
szsdlc schedule WI-0051 --horizon now --top
szsdlc unschedule WI-0051
```

`validate` then enforces what a prose priority list never could: every
`schedulable` entity that has reached the configured ready state appears
exactly once, no entity appears twice, nothing dangles, and no
non-`schedulable` type (an idea, a requirement) has leaked in.

## Command surface contract

Every command is consumed by an agent, so both halves cost tokens: a
hard-to-produce input causes retry loops (each failure costs the input, the
error and a re-think), and a verbose output pollutes context for the rest of
the session. Six rules govern the whole surface.

**C1 — Mutations report the resulting state in one line.** `set`, `link`,
`order`, `refine` and friends print the post-state so no confirming `show` is
ever needed. Eliminating that follow-up read is worth more than any output
trimming.

**C2 — Every refusal names the fix, on stderr, in at most three lines.**
The target is **two attempts at most**: the first call fails, the second call
*is* the suggested fix. That is only achievable if stderr is explicit enough to
act on without re-reading docs or guessing. Fixed shape:

```
line 1   <ref-or-arg>: what is wrong, with the specific values
line 2   Fix: <a runnable command>
line 3   (optional) See: <one reference>, only when no single fix exists
```

Concretely:

```
WI-0042: status executing → done blocked, 7/12 tasks unchecked.
Fix: szsdlc set WI-0042 status=review
```

```
set: 'relations' is not settable.
Fix: szsdlc link WI-0042 implements REQ-0007
```

```
no such entity 'WI-0420'.
Fix: szsdlc show WI-0042
```

Where genuinely no single fix exists, line 2 offers the **diagnostic** command
that reveals the answer (`Fix: szsdlc list --type REQ --status approved`)
rather than prose advice. An error that ends in something the agent can run is
the difference between two calls and five.

**C7 — stderr is bounded and machine-shaped.** No Python traceback ever
reaches stderr; every internal exception is converted to the C2 shape. Argparse
usage dumps are suppressed on error — a 30-line usage block is the classic way
a single typo costs a thousand tokens. Exit codes are distinct per class
(2 = bad input, 3 = refused by a gate, 4 = validation failed, 5 = config
error) so a caller can branch without parsing text.

**C3 — One job per command, with cross-references on overlap.** `set` refuses
to touch `relations` and says `use: szsdlc link WI-0042 implements REQ-0007`. Nested or list-valued fields are never edited through
`set`, because composing them on a command line is exactly the input that takes
an agent three attempts.

**C4 — Silent on the happy path when hook-invoked.** `sync` and `validate`
print nothing on success. They run after every file write and at every turn
end; output on the happy path has no consumer and risks reaching context.
`--verbose` opts in.

**C5 — Human output is the compact default; `--json` is for scripts.** JSON is
the more verbose encoding, so it is never the default an agent falls into.

**C6 — No unbounded output and no silent truncation.** Default `--limit 20`,
always print the total when truncated.

### Per-command audit

| Command | Input shape | Success output | Budget |
|---|---|---|---|
| `capture [text]` | one arg, **or stdin, or `$EDITOR`** — never requires quoting a multi-line body | the new id, one line | 1 line |
| `refine <ref> --into T [--title]` | two short args | new id + idea's new status | 1 line |
| `inbox` | none | id, age, first line each | ≤20 rows |
| `drop <ref> --reason "..."` | short quoted string, **or stdin** | confirmation | 1 line |
| `new <T> --title "..."` | two short args | new id + path | 1 line |
| `set <ref> f=v ...` | scalar fields only (C3) | `<ref>: status executing → review` | 1 line |
| `tag`/`untag <ref> <tag>...` | bare words, no flags | resulting tag list | 1 line |
| `link\|unlink <ref> <rel> <ref>` | three tokens, no flags | the edge, plus the generated inverse | 1 line |
| `convert <ref> <T>` | two args | new id, tombstone note | 2 lines |
| `log <ref> "msg"` | short arg **or stdin** | nothing | 0 lines |
| `schedule <ref> --horizon H [--after REF]` | one verb, one ref; roadmap defaults when one exists | the entity's new neighbours | 1 line |
| `unschedule <ref>` | one ref | confirmation | 1 line |
| `next` | none, or one filter flag | id, status, title per row | ≤10 rows |
| `show <ref> [--context]` | one ref | frontmatter + body, or budgeted context bundle | char cap |
| `context` | none | in-flight entities + counters block | hard cap |
| `list [filters]` | flags only | one row per entity | ≤20 rows + total |
| `trace <ref> [--depth N]` | one ref, **default depth 2** | compact edge notation | ≤20 edges + total |
| `sync` | none | **nothing** | 0 lines |
| `validate` | none | **nothing** when clean; grouped findings when not, most severe first | 0 / ≤20 |
| `standards match <path>...` | paths | matching standard names | ≤10 rows |
| `init` | none | created paths, compact | ≤15 lines |
| `--help` | none | one line per command | ≤25 lines |

Unknown-reference errors suggest the nearest match (`no WI-0420; did you
mean WI-0042?`), which converts the most likely agent typo into a single
corrected call rather than a search.

No sub-verbs and no positional roadmap name; `--roadmap` defaults when only one exists.
- [ ] **Step 3:** Reject scheduling of non-`schedulable` types and of entities that have not reached the configured ready status.

## Phase 2 — CLI

### Task 7: Capture and refinement
- [ ] **Step 1:** `szsdlc capture [text]` — accepting an argument, stdin, or `$EDITOR`; creates one `intake` entity with minimal frontmatter. Must complete in a single command with no prompts, since capture cost is the whole point.
- [ ] **Step 2:** `szsdlc refine <idea-ref> --into <TYPE> [--title ...]` — create the typed entity, write `refined_from` on the child only, and advance the idea to `refining`/`refined` per config.
- [ ] **Step 3:** `szsdlc inbox [--json]` — unrefined ideas, oldest first.
- [ ] **Step 4:** `szsdlc drop <idea-ref> --reason "..."` — terminal, never deletes.
- [ ] **Step 5:** Tests: capture from all three input modes, multi-spawn from one idea, drop-with-reason, refusal to refine an already-refined idea; commit.

### Task 8: Entity commands
- [ ] **Step 1:** `szsdlc init` — scaffold `.szsdlc/config.yml`, directories, an empty roadmap and starter templates.
- [ ] **Step 2:** `szsdlc new <TYPE> --title "..."`, for entities created directly rather than via refinement.
- [ ] **Step 3:** `szsdlc set <ref> <field>=<value>...` — enforce the type's transition graph and gates (`requires_artifact`, `requires_tasks_complete`), refusing with the reason.
- [ ] **Step 4:** `szsdlc link` / `unlink` — write the edge on the authoring side only, enforcing allowed types and cardinality.
- [ ] **Step 5:** `szsdlc convert <ref> <TYPE>` — mint the new id, move contents, map or reset status, write `supersedes`/`superseded_by`, leave a resolving tombstone.
- [ ] **Step 6:** `szsdlc log <ref> "msg"` — append a dated line to the journal artifact. Sole writer of that file.
- [ ] **Step 7:** `szsdlc schedule` / `unschedule` exposing Task 6's operations.
- [ ] **Step 8:** Tests for each including every refusal path, and a convert round-trip asserting old references still resolve; commit.

### Task 9: Query commands (the token-saving surface)

> **Design rule — counters in context, details on demand.** Every condition
> worth knowing about is a *scalar* in `szsdlc context`, costing a handful of
> tokens at session start. The corresponding listing is only spent when the
> scalar is non-zero and the detail is actually wanted. No listing is ever
> unbounded, and no truncation is ever silent.

- [ ] **Step 1:** `szsdlc next [--horizon H] [--parent <ref>]` — actionable queue drawn only from `actionable` types, **ordered by roadmap position** rather than a per-entity field, filtered to entities whose `depends_on` are all terminal. Under ~40 lines of output.
- [ ] **Step 2:** `szsdlc show <ref> [--context]` — `--context` adds design summary, current unchecked task, recent journal entries, immediate relations and provenance, budgeted to a character cap.
- [ ] **Step 3:** `szsdlc context` — the `SessionStart` payload: in-flight entities, the current task, and a **counters block** — inbox depth, unscheduled count, uncovered-requirement count, validation error and warning counts. Counters are scalars, never lists. Hard cap, deterministic ordering.
- [ ] **Step 4:** `szsdlc list [--type T] [--status S] [--tag T]... [--parent <ref>] [--uncovered] [--unscheduled] [--limit N] [--json]` and `szsdlc trace <ref> [--depth N]` walking relations both directions, including back to the originating idea.
- [ ] **Step 5:** Apply the output contract to **every** listing command: a default `--limit` (20), a printed total whenever results are truncated (`showing 10 of 47 — rerun with --limit 0`), and `--json` exempt from limits for programmatic use. Truncation must always be visible, since a silently capped list reads as "nothing more to see".
- [ ] **Step 6:** `szsdlc standards match <path>...`.
- [ ] **Step 7:** Tests asserting output stays under the caps for a 200-entity fixture, **including a fixture where every entity is unscheduled** — the migration case, and the one where an uncapped listing would hurt most; commit.

### Task 9a: Enforce the command surface contract
- [ ] **Step 1:** Implement C1 — every mutating command prints the resulting state in one line, so no confirming `show` is ever required.
- [ ] **Step 2:** Implement C2/C7 — a shared error type carrying `problem`, `fix` and `exit_code`, rendered to stderr in the fixed three-line shape. `fix` must be a runnable command. Suppress argparse usage dumps and convert every internal exception, so no traceback can escape.
- [ ] **Step 2a:** **Two-shot recovery tests.** For every error class, assert mechanically that (a) stderr is ≤3 lines, (b) it contains a `Fix:` line, (c) the fix line parses as a valid invocation, and (d) **executing that suggested command actually succeeds** against the same fixture. This makes "correct in two shots" an enforced property rather than an aspiration — a fix hint that doesn't work fails CI.
- [ ] **Step 3:** Implement C3 — `set` rejects `relations`, list-valued and nested fields, naming the correct command instead.
- [ ] **Step 4:** Implement C4 — `sync` and `validate` are silent on success, `--verbose` opts in. Assert byte-count zero on the clean path, since these run on every edit and every turn end.
- [ ] **Step 5:** Implement nearest-match suggestions for unknown references (edit distance over known ids, best single suggestion only).
- [ ] **Step 6:** Compact `--help`: one line per command, deep help behind `<command> --help`.
- [ ] **Step 7:** **Golden output-budget tests**: for every command in the audit table, assert the success output stays within its stated budget against both a 20-entity and a 200-entity fixture. The table is the specification; a command that outgrows its budget fails CI.
- [ ] **Step 8:** Commit.

## Phase 3 — Sync and validation

### Task 10: Sync engine
- [ ] **Step 1:** Implement `render.py`: project template overrides falling back to bundled defaults, plus a `compare()` primitive returning which generated files would differ from disk.
- [ ] **Step 2:** Emit a `<!-- GENERATED by szsdlc — do not edit -->` banner plus a source-hash line into every generated file.
- [ ] **Step 3:** Ship default views. "List my ideas", "list all requirements" and "list all epics" are genuinely different questions, so they get different views rather than one index with filters:
  - `inbox` — unrefined ideas, oldest first, with age
  - `roadmap` — horizons in order, each listing its scheduled entities in sequence
  - `board` — work only (`actionable` types), grouped by status, sub-grouped by parent epic
  - `tag-index` — every tag with its count and entities, answering "what touches DNS" without a relation walk
  - `epic-rollup` — each epic with children and derived aggregate progress; closed epics drop off
  - `requirements-register` — every requirement including retired, with derived `covered`/`delivered`, uncovered rows flagged, never pruned
  - `traceability` — requirements against what implements them, and entities back to their originating idea
  - `decisions` — the ADR log
- [ ] **Step 4:** **Degrade visibly, never silently.** An unresolved reference renders as `WI-0420 (missing)`; an unparseable entity appears in the relevant view with its path and error. Dropping broken edges would let `sync` conceal exactly what `validate` exists to surface. Test with a fixture whose graph is deliberately broken.
- [ ] **Step 5:** Implement **records**: load each configured YAML dataset, validate against its schema, render through its template.
- [ ] **Step 6:** `szsdlc sync` — regenerate every view and record. **Sync never validates.** It must succeed against a broken graph, because intermediate states are legitimately invalid (an entity exists before it is linked, is linked before it is scheduled) and because views are most needed when something is wrong. Rendering is permissive; validation is strict. There is no `--check` flag — staleness is a `validate` rule, so CI and pre-commit ask one question, not two.
- [ ] **Step 7:** Tests; commit.

### Task 11: Validation rules
- [ ] **Step 1:** Implement `validate.py`, one function per rule, each returning `(level, ref, message, fix_hint)`:
  - unparseable entity files, reported with path and parse error
  - frontmatter schema violations; duplicate ids; id not matching its filename/directory; id not matching the configured pattern or key
  - dangling relation targets; cycles (including `parent`); disallowed relations; cardinality violations
  - references to a tombstoned id (warning, with the rewrite as fix hint)
  - status/artifact disagreement; status/progress disagreement (only for `tracks_progress` types)
  - a work item with no `parent`, or a `parent` whose type is not `can_parent`
  - **roadmap:** a ready `schedulable` entity absent from every roadmap; an entity scheduled twice; a scheduled entity that is terminal; a non-`schedulable` type scheduled
  - **tags (warnings only, never errors):** two tags within edit distance 1 of each other (likely typo — `dns` vs `dsn`); a tag used exactly once once the total tag count passes a configured threshold (sprawl signal)
  - **intake:** an idea in `refined` with no spawned children; an idea in `inbox` older than a configured threshold (warning — the inbox is going stale)
  - **warning:** an `approved` requirement nothing implements; a work item implementing a `draft` or `retired` requirement
  - broken `[[wikilinks]]` and relative markdown links; orphan files in entity directories
  - stale generated files — a first-class rule like any other, implemented with the render module's `compare()` primitive. `validate` is the umbrella; rendering is a mechanism it borrows
- [ ] **Step 2:** Every finding is a statement about the **project**. A broken *model* invariant is a `szsdlc` bug, so it raises an internal error on the C7 channel instead of appearing as a finding — the two must never be conflated in output.
- [ ] **Step 3:** `szsdlc validate [--json]`; exit 1 on errors, 0 on warnings only.
- [ ] **Step 4:** Fixture project exercising every rule passing and failing.
- [ ] **Step 5:** Commit.

## Risks

| Risk | Mitigation |
|---|---|
| Windows interpreter resolution in hooks | Task 12 tests Git Bash, PowerShell and WSL before hooks are written |
| Capture stays too expensive and the inbox dies | Single-command capture with no prompts is an explicit acceptance criterion in Task 16 |
| Inbox becomes a graveyard | `validate` warns on ideas older than a configured threshold; `drop --reason` makes killing an idea a first-class outcome rather than neglect |
| Roadmap file becomes a merge-conflict hotspot | One entity per line, stable formatting, script-only edits; conflicts resolve as line-level adds |
| A listing dumps hundreds of lines into context during migration, when everything is unscheduled | Counters in `context`, `--limit 20` default on every listing, visible truncation; a fixture test covers the all-unscheduled case |
| Full-graph load on every hook invocation gets slow at scale | Benchmarked at 200 and 2000 entities in Task 16; caching deferred unless measured, since a stale cache is the failure mode being eliminated |
| Directory-scan id allocation races across worktrees | Ids allocated at creation, never renumbered; `validate` reports duplicates with both paths |
| Free tags sprawl, or split silently on a typo | Normalized at the single write path; `validate` warns on near-duplicates and singletons, surfaced as a counter in `context` rather than a listing |
| Type-in-id makes reclassification expensive | Typeless intake keeps `convert` off the common path; tombstones and stale-reference warnings cover the rest |
| Frontmatter round-trip corrupts hand-written files | Property test in Task 4 gates the whole design |
| Skills drift back into carrying procedure | 50-line budget enforced at review |
| Over-generalising before a second consumer exists | Genericity proven by `examples/`, not by speculative config surface |
